# Sweeper-Maid 垃圾箱改造计划书

> 版本：1.0 | 日期：2026-08-07 | 状态：待执行
> 本目录 `docs/` 已被 `.gitignore` 忽略，仅本地存档，不提交仓库。

---

## 1. 背景与目标

Sweeper-Maid 是一个 NeoForge 1.21.1（`neo_version=21.1.224`，Java 21）的空物品清理模组：周期性扫描掉落物，存入"垃圾箱"容器，玩家用 `/sweepermaid dustbin <index>` 打开垃圾箱取回物品。

现状痛点：

1. 垃圾箱是**固定数量**（配置 `DUSTBIN_COUNT`，默认 8），每箱 54 格（6×9）。
2. 每格只按物品自身最大堆叠（默认 64）叠加，量大时容易堆满、溢出丢弃。
3. 界面是原版箱子界面，**没有翻页控件**，只能靠命令切换 index。

本次改造目标（用户需求）：

- **A. 翻页界面**：GUI 顶部左侧增加「上一页 / 文本显示 1/9 / 下一页」，文本含义为"当前页/总页数"。
- **B. 动态页数**：页码范围不再固定，**总页数动态生成，第 1 页放满（54 种物品）才启用第 2 页**，合理精简时自动回收空页。
- **C. 超大堆叠**：把每格堆叠上限从物品原 64 改为**配置项 `DUSTBIN_SLOT_CAPACITY`（默认 1,000,000）**，一格一种物品，数量可一直累加而不挤满。
- **D. 排序**：**全局重排**（用户已确认）——每次清扫结束后，全桶按"物品数量从大到小"排序，再重新打包页面（第 1 页永远是数量最多的 54 种），空页自动移除。

## 2. 关键决策（已与用户确认）

| 决策点 | 结论 |
|---|---|
| 排序范围 | **全局重排**：清扫后收集全部种类 → 按数量降序 → 重新打包，第 1 页 = 数量最多的 54 种；空页删除。 |
| 取走行为 | **每次左键最多取走 64 个**（右键=取一半按上限裁剪到 64）；Shift 单击维持原版"能装多少装多少、多余留桶"逻辑。 |
| 每格容量 | 新增配置 `DUSTBIN_SLOT_CAPACITY`（默认 1_000_000，范围 1 ~ 2_147_483_647）。 |
| 旧配置去向 | 删除 `DUSTBIN_COUNT`（动态页数取代固定数量）。（用户未明确反对，作为合理假设写入） |
| 每页容量 | 保持 54 格（6×9 大箱子界面）。 |

## 3. 核心技术事实（已对照 NeoForge 21.1.224 官方源码逐一验证）

这些事实决定实现方案，是本次改造的**依据**：

1. **内存中 ItemStack 数量无上限**：`ItemStack.setCount(int)` 无任何钳制（源码 `ItemStack.java`），int 上限约 21 亿。
2. **NBT 存档上限 = 99**：`ItemStack.CODEC` 对 `count` 字段使用 `ExtraCodecs.intRange(1, 99)`；`SimpleContainer.createTag/fromTag` 全量走该 CODEC，因此**堆叠 >99 直接复用旧存取会存档失败/损坏**。
   → 必须给垃圾箱容器**自定义序列化**：每槽存 `{stack:{id,components…}, count:<int>}`，`stack` 用 `ItemStack.SINGLE_ITEM_CODEC`（不编码 count）编码，count 单独存 int。
3. `SimpleContainer.setItem()` 会按 `getMaxStackSize(stack)`（默认 min(64, 物品上限)）裁剪数量；`canAddItem()` 也按物品自身上限判断。
   → 自定义容器需覆写 `getMaxStackSize()` 与 `getMaxStackSize(ItemStack)` 返回 `DUSTBIN_SLOT_CAPACITY`，并覆写 `canAddItem`。覆写后 `addItem()` 的"同种合并优先、空槽其次"逻辑自动满足"一格一种、可一直叠加"。
4. 网络同步无限制：`ItemStack.OPTIONAL_STREAM_CODEC` 用 VarInt 写数量，菜单数据同步、翻页无需担心。
5. `ChestMenu` 使用原生 `Slot`；`Slot.getMaxStackSize(stack) = min(容器上限, 物品上限=64)`，且 `safeInsert` 会按它钳制 → 自定义 `Slot` 覆写 `getMaxStackSize(ItemStack)` 返回桶容量。
6. 原版箱子界面无法新增按钮 → 必须**自定义 Screen + 自定义 MenuType + 网络 Payload**。

## 4. 技术与算法设计

### 4.1 翻页界面架构（MenuType + Screen + Payload + DataSlot）

- 自定义 `MenuType<DustbinMenu>`（注册到 `Registries.MENU`）。
- 服务端打开：`player.openMenu(new MenuProvider(...))`，`createMenu` 返回 `DustbinMenu(页码)`，容器取 `SMSavedData.getDustbedPage(page)`。
- 客户端：`MenuScreens.register(类型, DustbinScreen::new)`（`@EventBusSubscriber(Dist.CLIENT)`）。
- 当前页与总页数通过 **两个 DataSlot** 同步（`addDataSlot`）：
  - `DATA_PAGE`（0-based 当前页）、`DATA_PAGE_COUNT`（总页数）。`broadcastChanges()` 时刷新。
- 翻页：客户端点击按钮 → 发送 `PageChangePayload(delta=±1)` → 服务端校验后再次 `openMenu`（界面重开为常见做法）。
- Screen 背景直接用原版 `textures/gui/container/generic_54.png`（六行箱子贴图，无新增资源）。

### 4.2 排序算法（回答"能不能用更好的算法"）

- `n` = 垃圾箱中物品种类总量，通常几十~几百；**瓶颈不在排序本身**。
- Java `List.sort()`/`Collections.sort()` 用的是 **Timsort**：近乎有序时趋近 O(n)，最坏 O(n log n)。
- 每次清扫只有少量种类的数量上升，序列天然"近乎有序"，Timsort 正好发挥 O(n) 能力。
- **冒泡排序是 O(n²)，最坏与平均都劣于 Timsort，直接排除**。
- 最终流程：`collectAllStacks() → 同种合并（防溢出重复格）→ 按 (count desc, itemId string asc) 稳定排序 → 每页 54 槽重新打包 → 丢弃空页`，整段 O(n log n)，每次清扫执行一次即可。
- 追加边界：若某类数量超过单格容量（默认 100 万，几乎不会发生），打包时拆为"同种多格"，排序按合并后总量参与。

### 4.3 数量安全（防 >99 存档崩溃）

- 取走：`DustbinSlot.tryRemove(amount, decrement, player)` 将 amount 裁剪到 `min(amount, 64)`，左键/右键均不会带出 >99 的旅程栈。
- 放置：`DustbinSlot.getMaxStackSize(ItemStack)` 返回桶容量，放进任意大堆（实际客户端游标已 ≤64）不缺省。
- Shift-click：沿用原版 `moveItemStackTo`（目的地槽各自上限 64），游标不会超限；剩量留桶，天然安全。
- 玩家背包：max 64，永无 >99 保存风险。

### 5. 数据迁移（NBT 兼容）

- 新格式（每槽）：`{ "stack":<SINGLE_ITEM_CODEC 编码>, "count":<int> }`。
- 读旧档：若槽标签含 `"id"`（旧 `SimpleContainer.createTag` 格式）→ 用 `ItemStack.parse` 兼容解析并套用原数量。
- 加载时将 count 钳到当前容量上限（防改小配置后溢出）。

## 9. 全局掉落物过载自动清扫（追加需求，2026-08-07，已与用户逐项确认）

背景：掉落物堆积导致服务器卡顿（TPS 下降），希望不等定期间隔，在掉落物过多时自动提前清扫一次。

| 决策点 | 结论（用户确认） |
|---|---|
| 目的 | 防服务器卡顿，无论玩家是否在线 |
| 统计口径 | **按堆**：`ItemEntity` 实体个数（每坨算 1，与其堆叠数无关） |
| 计数方式 | `EntityJoinLevelEvent` +1 / `EntityLeaveLevelEvent` -1（O(1)，无需扫描；清扫 discard 时自动归零） |
| 阈值 | 新配置 `GLOBAL_ITEM_COUNT_THRESHOLD`，默认 5000，范围 1 ~ Integer.MAX_VALUE |
| 触发行为 | 复用完整清扫流程 `doSweeping`（进垃圾箱 + 黑名单删 + 排序 + 存档） |
| 冷却 | 新配置 `OVERLOAD_SWEEP_COOLDOWN`，默认 60 秒（触发后该时长内不再因超阈值触发） |
| 定时器 | 触发额外清扫时重置 `sweepTickRemain`（定时倒计时重计） |
| 提示 | 清扫完成后给**所有在线玩家**发消息；文案可配置（空走 lang），X = 本次清扫的掉落物堆数（进垃圾箱的 + 黑名单直接删的，白名单不算） |
| 检查频率 | 每 tick（O(1) 判断） |
| 禁用 | `ITEM_SWEEP_INTERVAL = 0` 时一并禁用 |
| 消息示例 | zh："[扫帚女仆]：才扫一会儿就又有 %s 堆垃圾啦？没办法只好继续扫了~"（`$1`=堆数） |
| lang 键 | `sweeper_maid.message.overload_sweep`（en + zh） |

实现要点：
- `SweeperMaid` 新增字段 `itemEntityCount`、`lastOverloadSweepTick`、`lastSweepWasOverload`。
- `onTickPre` 中（interval≠0 时）每 tick 判断：`itemEntityCount > threshold && !toSweep && tick - lastOverloadSweepTick >= cooldownTicks` → 置 `toSweep=true`、重置定时器、记录触发 tick、标记本次为过载清扫。
- `doSweeping(server, boolean overloadSweep)`：新增堆数统计（`checkAndCollectEntity` 的 ItemEntity 分支无论黑白名单每堆 +1）；overloadSweep 时清扫末尾向所有在线玩家发送提示消息。
- 配置新增：`GLOBAL_ITEM_COUNT_THRESHOLD`、`OVERLOAD_SWEEP_COOLDOWN`、`MESSAGE_OVERLOAD_SWEEP`（默认空=走 lang）。
- GameTest 新增：事件计数随 spawn/discard 正确增减（反射读计数，`runAfterDelay` 分阶段断言）。

## 10. 经验实体收集（追加需求，2026-08-07，已与用户逐项确认）

背景：经验球（`ExperienceOrb`）过多同样造成卡顿；玩家希望清扫时收集经验而非丢弃。

| 决策点 | 结论（用户确认） |
|---|---|
| 收集方向 | 清扫时把经验球折算成**附魔之瓶**（`experience_bottle`）物品存入垃圾箱，玩家从垃圾箱取回 |
| 过载计数 | 经验球计入 `itemEntityCount`，与掉落物**共享**过载阈值（默认 500） |
| 兑换比例 | 新配置 `XP_PER_BOTTLE`（默认 10）：总经验 X ÷ 10 向上取整 = 瓶子数 Y（附魔之瓶开瓶 3~11 经验，折损防刷） |
| 提示 | 清扫后聊天消息**追加**一句"其中 X 的经验已经转换成 Y 个附魔之瓶"（X=总经验，Y=瓶子数；仅收集到经验时），走 lang + 配置 |
| 放入 | 附魔之瓶进垃圾箱，大容量堆叠，正常参与全局排序 |
| 白名单 | 经验球全部收集，不受物品白/黑名单影响 |

实现要点：
- `checkAndCollectEntity` 新增 `ExperienceOrb` 分支：累加 `orb.getValue()`（经验值）+ `sweptItemPiles.incrementAndGet()`（计入堆数）+ `killedEntities.add`（discard）。
- `doSweeping` 末尾：总经验 > 0 时，`bottles = ceil(totalXp / XP_PER_BOTTLE)`，`instance.addItemToDustbin(new ItemStack(Items.EXPERIENCE_BOTTLE, bottles))`。
- 聊天消息（`CHAT_MESSAGE_AFTER_SWEEP`）追加转换提示，lang 键 `sweeper_maid.message.xp_converted`（`$1`=经验、`$2`=瓶子数），配置项 `MESSAGE_XP_CONVERTED`。
- 新增配置 `XP_PER_BOTTLE`、`MESSAGE_XP_CONVERTED`；lang en/zh；config-examples 同步。
- GameTest：经验球 → 附魔之瓶换算与入桶逻辑。

## 7. 风险备注

- 翻页会关闭并重新打开界面（轻微闪烁），这是常见做法，接受。
- 玩家在清扫发生的同时开着垃圾箱：界面内容可能因重排变化；总页数实时刷新（DataPage 广播）。
- 容量默认 100 万/槽，一页 5400 万，几乎不可能写满；溢出的边界行为（同类多格）已按合并处理。
